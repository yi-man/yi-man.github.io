## 一、从现象说起

你发出一个消息，等了几秒，回来的答案语焉不详——明明昨天同样的问题答得头头是道，今天却仿佛换了个人。这不是错觉，也不是模型本身变了。这是推理系统在高峰期为了扛住压力，做了一系列工程上的妥协。

## 二、一个请求的完整旅程

**正常情况下**，你的请求要依次经过这几道关：

第一步是**网络接入与负载均衡**。你的请求先到达服务商的入口节点，负载均衡器把它分配给某一个推理副本。正常时段，副本们都比较闲，选择空间大。

第二步是**请求排队**。推理引擎同时只能处理有限数量的请求，超出容量的先排队等待。正常时段队列几乎是空的，你感知不到延迟。

第三步是**Prefill（前填充）阶段**。这是计算密集的部分：GPU 把你的整个 prompt 一口气读进去，计算每个 token 的注意力权重，并把结果存进 KV Cache（键值缓存）。这一步越完整，模型对你说过的话记得越清楚。

第四步是**KV Cache 管理**。KV Cache 本质上是模型的"工作记忆"，存在 GPU 显存里。有了它，生成后续 token 时不用重新算前面的内容，速度才能快起来。

第五步是**Decode + 动态 Batching（批处理）**。推理引擎把多个请求的 Decode 步骤打包在一起，在 GPU 上并行跑，以提高吞吐量。这是现代推理系统提速的核心手段。

部分系统还会叠加一层**投机解码（Speculative Decoding）**：先用一个小的草稿模型快速生成几个候选 token，再交给大模型验证，接受就保留，拒绝就重算，整体加速明显。

最后是**采样与参数控制**——temperature、top-p、max_tokens——决定输出的随机性和长度。

这一套走下来，你才看到屏幕上的文字一个个流出来。

## 三、高峰期：哪些地方出了问题

高峰期并不是某个工程师走过去按下了"降智模式"的开关，而是多个层面的压力叠加，触发了系统的自动保护机制，或是系统本来就预设了降级策略。两类原因都有。

### 3.1 机器自动调节的部分

**动态 Batching 扩张**：这是完全自动的。vLLM、TensorRT-LLM 等推理框架会根据当前队列长度实时决定 batch size。高峰期队列暴涨，框架自动把更多请求打包进同一个 batch。batch 越大，每个请求能分到的 GPU 显存越少，KV Cache 的存储空间被压缩。

**KV Cache 驱逐策略**：同样是自动触发。当 GPU 显存不够用时，系统按照 LRU（最近最少使用）或其他策略把较早的 token 的缓存踢出去。结果是模型"忘记"了你在对话前段说过的内容——它实际上没有读到那些上下文。

**投机解码的降级**：草稿模型本身也是跑在 GPU 上的，高峰期它自己也过载，生成速度跟不上，接受率（acceptance rate）下降，系统自动回退到标准的逐 token decode。这步并不影响质量，但会拖慢速度，间接延长了整个推理时间，使后续步骤更紧张。

**负载均衡的随机性**：你的请求可能被分配到一个"亚健康"副本——GPU 型号偏旧、内存已经碎片化、或者本地 KV Cache 已经被频繁驱逐。不同副本之间的体验就不一致了。

### 3.2 人为预设的降级策略

并不是所有降级都是机器临时起意的，很多是服务商提前设计好的"高负载预案"：

**上下文长度的动态上限**：部分系统会在高负载时自动降低允许的最大 context 长度。你明明发了 8K token 的对话，系统只喂给模型 4K。这是一个在代码里写死的阈值，满足条件就触发，不会通知用户。

**量化策略的切换**：服务商可以预先设置：当 GPU 利用率超过某个百分比，就把推理精度从 FP16 切换到更激进的 INT8 甚至 W4A8。这个决策是人为的，执行是自动的。用户感知到的就是逻辑推理能力明显下降。

**采样参数的悄悄调整**：这是最隐蔽的一类。高峰期系统可能在后端调高 temperature（让输出更随机，也更"省力"），或者缩短 max_new_tokens 的实际生效值，让模型提前截断输出。这些不会写进 API 文档，用户根本看不见。

## 四、有没有办法解决

### 官方侧能做什么

最根本的解法是**扩容和异构调度**——部署更多推理节点，用专属的 prefill 集群和 decode 集群分别处理不同阶段的压力（prefill-decode 分离架构）。这方面已经有一些大厂在做，但成本高昂。

**对高价值用户/付费层提供资源隔离**，把它们的请求打到独立的副本池，不与免费用户共享资源，可以明显改善高端用户的高峰体验。

另外，服务商可以把降级做得**更透明**：当上下文被截断或量化精度切换时，在响应头或 API 字段里告知调用方。目前几乎没有服务商这么做，但这对开发者非常有价值。

### 用户/开发者侧能做什么

**错峰使用**是最简单的策略。对于不紧急的批量任务，放在深夜或凌晨跑，往往能得到更稳定的输出质量。

**显式压缩上下文**比依赖模型自己处理更可靠。把长对话定期总结成摘要再续写，而不是一直追加。这样即使系统截断了早期内容，关键信息也已经被摘要保留了。

**调低 temperature 并固定随机种子**，可以减少高峰期采样参数被悄悄调整后的随机波动。虽然无法阻止服务端修改，但至少你的请求本身是确定性的，便于对比。

**对关键任务做输出验证**——让模型在输出结尾重述关键结论，或者加一个"请检查以上推理是否完整"的步骤。这不能防止降质，但能帮你发现输出是否被截断或逻辑跳跃了。

如果通过 API 调用，可以**监控 TTFT（Time to First Token）和整体延迟**，把它们作为当前服务质量的代理指标。延迟异常飙升往往是降级正在发生的信号，这时候可以选择重试，或者延后任务。

---

归根结底，高峰期降智是**吞吐量与单次质量之间工程权衡的体现**。这个 trade-off 在今天的推理架构下几乎无法完全消除，只能通过更好的资源隔离、更透明的降级通知，以及用户端更健壮的调用策略来缓解。
