> 四个图，讲透一个典型场景：本地有科学上网，内网有 API，中间只靠一条隧道。

## 一、场景：典型的三层困境

```
┌─────────────┐     ┌─────────────┐     ┌─────────────────┐
│  常用机器    │     │ 专门机器     │     │  目标 API        │
│             │     │ (内网VPN)    │     │  api.my-provider.com │
│  • Codex    │────▶│  • SSH服务   │────▶│  • nginx虚拟主机  │
│  • 本地代理  │     │             │     │                 │
│    (tun模式) │     └─────────────┘     └─────────────────┘
│  • 环境变量  │
│    http_proxy│
└─────────────┘
```

- **左边**：常用机器，跑着 Codex（AI 编程工具）。  
  本地有 Clash/Surge 的 tun 模式代理，负责科学上网，`http_proxy=http://127.0.0.1:10090`。
- **右边**：目标 API `api.my-provider.com`，只有内网能访问。
- **中间**：一台专门机器，连着内网 VPN，能访问目标 API。

**目标**：让 Codex 通过专门机器访问内网 API。

本质是一条 SSH 隧道的事，但实际调试中，代理、DNS、nginx 虚拟主机三个层面依次“拦截”，才引出最终的三步解法。

## 二、解法：三步对齐三层

```bash
# 1. SSH 隧道：本地 7999 → 专门机器 → 目标 API:80
ssh -N -L 7999:api.my-provider.com:80 admin@192.168.31.100

# 2. 改 hosts：让域名解析到本地
echo "127.0.0.1  api.my-provider.com" | sudo tee -a /etc/hosts

# 3. 启动 Codex 时排除该域名走代理
no_proxy="api.my-provider.com" codex
```

Codex 配置（示意）：
```toml
[model_providers.myclaude]
base_url = "http://api.my-provider.com:7999/v1"
```

这三步分别解决：**传输层**（隧道）、**DNS 层**（hosts）、**应用层**（代理排除）。下面用图拆解。

## 三、原理：三层各自独立，必须对齐

### 3.1 SSH 隧道：地下通道

```
常用机器                      专门机器                    目标 API
   │                            │                          │
   │  本地端口 7999              │                          │
   ├───SSH加密───▶              │                          │
   │                            ├───明文HTTP───▶          │
   │                            │                          │
   │                            │◀───响应────────────────│
   │◀───SSH加密─────────────────┤                          │
```

隧道把 `localhost:7999` 的流量送到目标机器的 80 端口，但目标 API 是 nginx 虚拟主机——它**不看端口，只看 Host 头**。

### 3.2 nginx 虚拟主机：看名片不看门牌

```
请求1: GET /v1  Host: localhost:7999   → nginx 404 (不认识)
请求2: GET /v1  Host: api.my-provider.com  → nginx 401 (服务找到了)
```

- 直接访问 `localhost:7999`，Host 头是 `localhost`，nginx 找不到对应网站 → 404。
- 修改 `/etc/hosts` 让域名指向 `127.0.0.1`，请求的 Host 头仍然是 `api.my-provider.com`，nginx 正确路由。

### 3.3 http_proxy 优先级：环境变量 > 系统 DNS

这是最隐蔽的坑。**tun 模式**修改路由表，但 `http_proxy` 让 HTTP 客户端**直接连代理**，完全绕过系统网络栈：

```
有 http_proxy:
  Codex → 代理(127.0.0.1:10090) → 代理转发失败 → 502

无 http_proxy（或 no_proxy 排除）:
  Codex → 查 hosts(127.0.0.1) → SSH 隧道 → 专门机器 → 目标 API ✅
```

`no_proxy` 的作用就是告诉 HTTP 客户端：“这个域名例外，走正常 DNS + 直连”。

## 四、三个报错 → 三层诊断

### 报错一：502 Bad Gateway

- **现象**：隧道建好，curl 到 `localhost:7999` 能通，但 Codex 报 502。
- **诊断**：502 来自本地代理（127.0.0.1:10090）。代理拿到目标 `api.my-provider.com:7999`，无法解析内网地址，转发失败。
- **本质**：请求根本没进隧道，被代理劫持了。

### 报错二：404（两种，原因截然不同）

| 请求方式 | Host 头 | 结果 | 原因 |
|---------|---------|------|------|
| `GET /v1` 直接连专门机器 | `api.my-provider.com` | 404 | 方法不对（API 只接受 POST），正常 |
| `POST /v1/responses` 走隧道 | `localhost:7999` | 404 | nginx 虚拟主机不认识该 Host |
| `POST ...` + 手动改 Host | `api.my-provider.com` | 401 | 服务找到了，缺认证 |

**快速定位**：用 `curl -H 'Host: api.my-provider.com' http://localhost:7999/v1/responses`，若返回 401 说明 Host 头对了。

### 报错三：改了 hosts 还是 502

- **现象**：`/etc/hosts` 已加映射，`curl localhost` 正常，但 Codex 仍 502。
- **诊断**：`curl -v` 输出第一行：
  ```
  * Uses proxy env variable http_proxy == 'http://127.0.0.1:10090'
  ```
- **本质**：`http_proxy` 优先级高于 hosts。加上 `no_proxy` 才真正绕开。

## 五、一句话总结

> **`no_proxy` 让应用层绕过代理 → hosts 让 DNS 层指向本地 → SSH 隧道打通传输层**  
> 三层独立，错一层都不通。

这个模式适用于任何“本地有透明代理 + 需要 SSH 隧道访问内网虚拟主机”的场景——不限于 Codex，curl、Python requests、Node.js fetch 都一样。
